1. 模型能力只是起点

真正让 Agent 稳定工作的往往不是更强模型本身，而是上下文组织、任务切分和失败恢复策略。

实用判断

如果问题主要卡在检索、工具失败、路径错误或状态不一致，单纯换更强模型往往不是最有效解。

常见错觉

把“Agent 不稳定”归咎给模型，其实更常见的原因是工作流没有留验证点。

2. 工具调用要显式建模

把可用工具看成接口能力集合，包括输入格式、失败模式、是否阻塞主流程，而不是把所有事情都留给模型自由发挥。

设计工具时可问：
- 输入是否足够小而明确？
- 输出能不能直接被下一个步骤消费？
- 失败时是否返回可行动信息？

3. 工作流比单次回答更重要

多步任务建议拆成：理解目标、取上下文、执行动作、验证结果、再修正。很多时候这比一条长 prompt 更稳。

一个常见流程：
plan -> inspect -> act -> verify -> summarize

如果任务复杂，再加:
branch -> parallel -> integrate
  • 需要跨文件或跨系统的信息时，优先先“inspect”而不是直接“act”。
  • 一旦存在副作用操作，最好单独插入“verify”阶段。
  • 长任务最好把上下文和目标分段，而不是一次塞满。

4. 评估与验证

Agent 的结果好不好，不该只看输出是否流畅，而应看它是否可执行、可追溯、可维护、可复现。

最小验证闭环

输出前至少确认：目标是否命中、路径是否存在、命令是否可运行、网页是否可访问、改动是否与需求一致。

高风险任务

涉及权限、金钱、生产环境、删除操作时，必须把验证和确认显式放进流程里。

5. 常见坑

  • 工具太多但没有使用边界
  • 缺少验证步骤，导致输出看起来对但实际不可用
  • 上下文堆得太满，真正关键约束反而被淹没
  • 过早下结论，没有先检查代码、文件或页面的真实状态
